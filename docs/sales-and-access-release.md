# Продажи и доступы MYSTERION INTERNATIONAL

## Состояние подготовки

Изменения подготовлены локально. Production, реальные заказы, выданные ранее
доступы, аккаунт владельца и аккаунт модерации не изменялись. Публикация,
production-миграция и включение публичных продаж не выполнялись.

Уже существовали: участники и сессии, Cloudflare Access для сотрудников,
`viewer_orders`, `viewer_grants`, ручное одобрение заявок, отзыв доступа,
проверка прав на уроки и видео, короткие подписанные Bunny URL,
личная библиотека, owner-only проверка магазина и проверка HMAC webhook.
Эти механизмы использованы повторно; новая административная система не создаётся.

## Реализация

В существующую панель добавлен раздел «Продажи и доступы»:

- Товары: цена RUB, бесплатный/платный режим, включение продажи, количество
  покупок/доступов. Доступ на 7/30/90/180 или своё число дней, бессрочно,
  индивидуальные даты. Платное видео требует Bunny; продажа требует готовой
  опубликованной записи и включённого защищённого просмотра.
- Ручные заказы: поиск проверенного активного участника по email, выбор товара,
  учёт суммы и способа фактически полученной оплаты. Частичные платежи
  не выдают полный доступ. После полной оплаты доступ выдаётся отдельным действием.
  Бесплатный доступ и подарок не создают фиктивную оплату.
- Отдельные состояния: ожидает, частично оплачено, оплачено, доступ выдан,
  отменено, возврат. Отмена неоплаченного заказа отличается от учёта уже
  фактически выполненного возврата. Ручной возврат на сайте **не переводит деньги**.
- Начало/окончание, продление, отзыв, история с материалом, участником и ролью
  исполнителя. Заказы, платежи, доступы и история имеют страницы по 50 записей.
  Список товаров использует существующий предел: до 200 видео и 200 курсов.
- Только владелец назначает существующему активному публикатору отдельное право
  управления продажами. Это право не открывает остальные разделы владельца.
- В интеграции видны флаги запуска и owner-only проверка Tribute Shop.

В кабинете участника показаны новая история оплаты и сроки доступа. Старые
заявки сохраняют прежний интерфейс. Для новых заказов старое ручное одобрение
и отправка заявки на проверку заблокированы: нельзя обойти новый учёт платежей.
В каталоге управляемый товар использует новый процесс покупки; выключенная
продажа недоступна также на сервере. Покупка уже доступной записи блокируется.
Тексты новых интерфейсов поддерживают RU/EN. DE не отображается; существующие
локализованные поля не перезаписываются при изменении условий продажи.

### Школа

Основной продукт: 3 000 000 копеек (30 000 ₽). Владелец указывает реальную
дату начала соответствующего потока. Обучение заканчивается через три
календарных месяца; записи доступны ещё шесть календарных месяцев после
окончания обучения. Конец месяца учитывается с ограничением по последнему
дню целевого месяца. Пример теста: 31.01 → 30.04 → 30.10.
Дата оплаты не переносит даты потока. Индивидуальное ручное разрешение
может иметь другие явно заданные даты; доступ можно продлить или отозвать.
Новые потоки и фактические даты мероприятий не придумывались.

### Tribute

Проверены официальные источники 11.11.2026:

- [Методы Shop API](https://wiki.tribute.tg/for-shops/api/methods)
- [Webhook и подпись](https://wiki.tribute.tg/for-shops/api/webhooks)
- [Официальная OpenAPI-схема](https://tribute.tg/api/v1/openapi/shop/en)

Используются `GET /shops`, `POST /shop/orders` и, для восстановления потерянного
ответа, `GET /shop/orders/{uuid}?shopId=…`. Цена передаётся в копейках,
`currency: rub`, `period: onetime`, фиксируются пользователь и локальный заказ.
Перед созданием проверяется выбранный `TRIBUTE_SHOP_ID`: активен,
`onlyStars === false`. Допустимая платёжная ссылка строго ограничена
`https://web.tribute.tg/shop/pay/{uuid}`. В Tribute создаётся разовый заказ,
а посетитель переходит на его страницу оплаты.

Нет предположения о поддержке Tribute заголовка Idempotency-Key. Создание
резервируется локально единожды. Если ответ потерян, автоматическое повторное
создание запрещено: состояние `uncertain`. Владелец находит уже созданный заказ
в Tribute и в новом разделе восстанавливает связь по UUID. Проверяются магазин,
сумма, валюта, разовый период, комментарий с локальным заказом и email.
Восстановление не создаёт новый платёж и не подтверждает оплату.
Если webhook приходит раньше сохранения UUID, для соответствующего ожидающего
заказа возвращается 503, чтобы Tribute повторил уведомление. Восстановление
нужно завершить в пределах срока повторной доставки; по документации это около
24 часов. Если подтверждение уже перестало повторяться, требуется сверка с
Tribute и отдельное решение владельца; redirect не используется как доказательство.

Существующий `POST /api/tribute/webhook` сначала проверяет HMAC-SHA256 от
исходных байтов тела через `TRIBUTE_API_KEY`. Выдача разрешена исключительно по
окончательному `shop_order` со статусом `paid`. Сверяются сохранённые UUID,
магазин, сумма, RUB и `customerId`; рекуррентный/пробный платёж не принимается.
Продукт определяется сохранённым локальным заказом, а не данными посетителя.
Относительный срок записи отсчитывается от времени подтверждённого события.
`shop_order_payment_received` и `shop_order_prepaid` не подтверждают покупку.
Неудачная попытка сохраняет возможность повторной оплаты без выдачи доступа.

`shop_order_refunded` учитывается по transactionId и фазе. `initiated` не
отзывает доступ; `completed` закрывает заказ и отзывает **только** связанный
с ним доступ. При частичном возврате применяется консервативная политика:
связанный оплаченный доступ также отзывается; независимые подарки сохраняются.
Возврат, пришедший раньше оплаты, не позволяет позднему событию выдать доступ.
`shop_order_cancelled` документирован для подписок; разовые покупки не
превращаются в подписку и не получают вымышленный сценарий отмены.
Возвраты денег через API и рекуррентные списания не инициируются.

Все изменения оплаты и выдача выполняются атомарными D1 batch.
У операций есть UUID запроса, отпечаток данных и уникальный nonce текущей
транзакции. Повтор или конкурентный повтор не создаёт ещё один платёж/доступ;
другие данные под тем же UUID отклоняются. `source_order_id` остаётся уникальным.
Повторы webhook идентифицируются по смысловому ключу события, а не sent_at.
Сырые уведомления, подписи, пароли и ключи не сохраняются в журнале.

### Защита и ограничения

Серверная проверка сессии, участника, начала/конца и отзыва доступа остаётся
в существующем механизме Bunny. Прямой запрос API без права не выдаёт токен.
Уже выданная подписанная ссылка может жить до трёх минут (и не дольше сессии
или разрешения); отзыв блокирует последующие выдачи, но не аннулирует уже
выданный URL мгновенно. Бессрочный доступ внутренне хранится как дата
31.12.9999; UI показывает «Бессрочно», Bunny URL всё равно краткосрочный.
Настройки самого Bunny (token authentication, embed/domain restrictions)
нужно подтвердить перед запуском; локальный тест не доказывает их фактическое
состояние у провайдера. Абсолютная защита от записи экрана не обещается.

## Проверки

Все новые данные — отдельные локальные SQLite/D1 fixture, без обращения к
production и реальных платежей. Команды используют Node 24; для импортов
платформы нужен существующий WASM loader:

```text
node --import ./tools/register-viewer-wasm.mjs tools/test-sales.mjs
node --import ./tools/register-viewer-wasm.mjs tools/test-sales-browser.mjs
node tools/test-sales-client-browser.mjs
node tools/test-sales-migration.mjs
node tools/test-sales-runtime.mjs
node --import ./tools/register-viewer-wasm.mjs tools/test-platform.mjs
node --import ./tools/register-viewer-wasm.mjs tools/test-viewer-auth.mjs
node tools/test-tribute-webhook.mjs
node tools/test-tribute-settings-browser.mjs
```

Браузерные снимки и JSON-результаты находятся в `output/sales-review/`.
Браузерные проверки охватывают RU/EN и ширины 320, 390, 768, 1440.
Runtime-проверка использует настоящий локальный Cloudflare workerd + D1,
production compatibility_date 2026-11-04 и не создаёт облачные ресурсы.

Результат: 99 API/сценарных проверок продаж, 57 браузерных проверок админки
(включая создание заказа, оплату, выдачу и подарок), 23 проверки интерфейса
участника, 7 проверок миграции на предварительно заполненной базе; runtime
workerd/D1 прошёл. Регрессии: 95 проверок платформы, 90 авторизации,
34 webhook и 31 существующих кнопок Tribute — прошли. Всего 436 проверок
плюс отдельный runtime-сценарий. Реальные платёжные запросы не выполнялись.

## Запуск по этапам

1. Подтвердить выкладку подготовленной ручной части. Сначала резервная копия D1
   и применение **только** `0011_sales.sql` к правильному production binding
   после проверки уже применённых миграций. Миграция добавляет таблицы/индексы
   и колонку ревизии; существующие суммы, статусы, пароли и сроки не меняет.
   Не применять всю папку повторно и не использовать разрушительные миграции.
2. Доставить изменения существующим GitHub → Cloudflare Pages процессом,
   сохранив production build и compatibility settings. Подготовленная копия
   содержит несвязанные старые WIP-изменения: выпускать только согласованный
   набор, не публиковать всю локальную ветку.
3. Для закрытого ручного режима: `SALES_ENABLED=true`,
   `SALES_PUBLIC_ENABLED=false`, `TRIBUTE_PAYMENTS_ENABLED=false`.
   Это не открывает публичную покупку. Нужны существующие Bunny-настройки и
   отдельная проверка перед `MEDIA_PAID_ENABLED=true`, если просмотр ещё выключен.
4. Владелец настраивает реальные товары, цену записей и даты потоков. Школа —
   30 000 ₽. Проверить закрытый сценарий на выделенном участнике/материале.
   Учётную запись владельца и модерации для этого не переиспользовать.
5. Только после подтверждения публичных продаж:
   `SALES_PUBLIC_ENABLED=true`. Ручные заявки работают независимо от Tribute.
6. После одобрения Tribute: owner-only проверка магазина, выбор его
   не секретного `TRIBUTE_SHOP_ID`, проверка `status=1`, `onlyStars=false`, URL
   webhook `https://mysterion-international.com/api/tribute/webhook`, контроль
   подписанного теста 200/401. Ключ остаётся прежним Cloudflare Secret.
7. Только после отдельного разрешения владельца:
   `TRIBUTE_PAYMENTS_ENABLED=true`, согласованная проверка реальной покупки и
   возврата. До этого реальная работа Tribute проверялась только фикстурами.

При отключении публичных продаж уже начатые Tribute-платежи продолжают
обрабатываться, если флаг Tribute остаётся включён. Не отключать обработку
webhook при наличии ожидающих платежей: выключенный флаг сохраняет прежний
режим приёма 200 без изменения заказов. Откат UI/backend не требует удаления
новых таблиц; исторические данные продаж сохраняются.
