# GetPlatinum v2 — подготовленная интеграция

Статус релиза: серверная интеграция подготовлена к Production с GETPLATINUM_LIVE_ENABLED=false. Реальные платежи и возвраты не выполнялись. Существующие покупки, доступы, Tribute и режим сайта сохраняются.

Официальные источники: https://getplatinum.ru/help/api/v2 и опубликованная этой страницей схема https://getplatinum.ru/docs/api-integration-v2.yaml?i=2 . Кабинет подтверждён владельцем: https://kepvalera.getplatinum.ru . Терминал 156040 хранится как справочная информация: в `InitPaymentUrlDto` нет параметра terminalId. Идентификатор организации API не приравнивается к номеру терминала.

## Реализация

- `POST /api/platform/sales/getplatinum/checkout`: существующая авторизованная сессия + существующий CSRF/rate limit; принимает ID видео, UUID запроса и контакт для чека. Сумму, валюту, название и срок читает сервер. Сумма браузера не принимается.
- Сервер обращается к `POST https://kepvalera.getplatinum.ru/api/public/v2/pay/init-payment-url` с Bearer-ключом. `dealId` — UUID заказа MYSTERION, `clientParams.clientId` — ID пользователя из серверной сессии. Проверяется `dealId` ответа и origin платёжной ссылки.
- Перед созданием проверяются активность организации и допустимый НДС через `/get-organization`. НДС выбирает владелец, значения по умолчанию нет.
- `GET /api/platform/sales/purchase-offer/:video` выбирает действующего провайдера. При Tribute использует прежнюю реализацию Digital Products; при GetPlatinum привязка Telegram не обязательна, текущий вход через Telegram/email сохраняется.
- `POST /api/getplatinum/webhook`: официальный v2 `X-Checksum`, uppercase hex HMAC-SHA256 **сырых байтов тела** с API-ключом, Web Crypto verify до разбора JSON. Ограничение тела 64 KiB, только JSON, в1 JSON-checksum не принимается. Нет сохранения/логирования ключей, исходных уведомлений или реквизитов карт.
- Тип 1: проверяет существующий заказ, успешный статус, целочисленные сумму/идентификатор платежа, RUB и уникальность платежа. Атомарно сохраняет оплату и создаёт прежний `viewer_grants` с уникальным `source_order_id`. Время начала — первое проверенное подтверждение сервером, срок — снимок существующих условий, не новый срок по умолчанию. Дубли не продлевают доступ.
- Тип 9: проверяет refundId, mdOrder, результат, сумму/валюту и общий размер возвратов. Полный подтверждённый возврат отзывает только право из соответствующего заказа. Частичный возврат сохраняет доступ до полного возврата; это правило следует подтвердить владельцу перед запуском. Другие ручные/подарочные права не затрагиваются.
- Возврат без суммы/валюты требует ручного разбора; новая автоматическая выдача по этому заказу запрещена. Возврат до оплаты учитывается и не позволяет позднему уведомлению выдать уже возвращённый доступ.
- Административные блокировки сохраняются; оплата их не снимает. Истёкший абсолютный срок требует ручного разбора.
- Неуспешное уведомление не отзывает ранее подтверждённый доступ. Сетевой сбой после отправки создания помечает заказ `uncertain`: слепое повторное создание запрещено. Такой заказ нужно сверить с GetPlatinum перед дальнейшими действиями.
- Возврат браузера на `successUrl` не подтверждает оплату. Кабинет опрашивает собственный серверный статус, доступ проверяется прежним серверным механизмом.
- Уведомления по существующим заказам принимаются даже при отключении новых продаж, смене провайдера и временном режиме сайта.

## Данные и административная панель

Миграция `media-worker/migrations/0017_getplatinum.sql` только создаёт настройки и таблицы метаданных/платежей/возвратов GetPlatinum. Исходные таблицы и CHECK-ограничения не перестраиваются. Используются общие `viewer_orders`, `viewer_grants`, журнал атомарных операций `sales_operations`. Прежние `sales_orders`/`sales_payments` с ограничением источников manual/tribute остаются неизменными; GetPlatinum хранит свои финансовые детали отдельно, с внешними ключами на общий заказ.

Значения после миграции: активный провайдер **Tribute**, GetPlatinum **выключен**, НДС **не задан**. Владелец видит настройки и журнал последних 100 заказов в `/admin-media` → «Продажи и доступы» → вкладка интеграций (существующая вкладка Tribute). API `/api/platform/admin/getplatinum` и `/check` доступен только владельцу, мутации защищены существующим CSRF. Старый ручной workflow не может подтвердить заказ GetPlatinum.

Срок берётся из единственного действующего сопоставления Digital Products для видео; если его нет — из включённых существующих условий товара. Неоднозначные или отсутствующие сроки блокируют покупку. Это не меняет интеграцию Tribute или её сопоставления.

## Cloudflare и активация

1. Проверить, что организация GetPlatinum разрешает API-платежи и кассовые настройки корректны. Получить организационный API-ключ.
2. В существующем тестовом окружении добавить **Secret `GETPLATINUM_API_KEY`**. Это единственный новый секрет, он же используется для проверки HMAC. Ключ сюда, в GitHub и логи не передавать. Tribute/Telegram/Bunny Secrets не менять.
3. `GETPLATINUM_API_ORIGIN` — необязательная несекретная переменная, значение по умолчанию `https://kepvalera.getplatinum.ru`; иной origin код не разрешает.
4. `GETPLATINUM_LIVE_ENABLED` — несекретный серверный запрет, отсутствует/`false` до разрешения. Ни один тест не требует включать его в Production. У официальной v2 схемы не обнаружен отдельный sandbox URL или флаг test: они не придуманы. Выполненные тесты используют локальные эмуляторы.
5. Применить 0017 сначала к отдельной тестовой D1 с существующей схемой и опубликовать тестовую сборку существующим процессом. Не направлять Preview на Production D1. Выполненная локальная проверка использует изолированные SQLite и настоящий D1 runtime Miniflare.
6. Владелец проверяет соединение и выбирает допустимый НДС. До разрешения на реальную контролируемую покупку GetPlatinum остаётся выключенным.
7. После отдельного разрешения: резервная копия D1, безопасная миграция Production 0017, публикация с GetPlatinum выключенным, проверка соединения владельцем. Для контролируемого запуска потребуется серверный флаг, включение GP и явный выбор провайдера в админке. Состояние публичных продаж/временного режима не меняется автоматически: оно тоже должно разрешать новые покупки.
8. После разрешённой контрольной покупки подтвердить сумму/чек, подписанный callback, выдачу ровно одного права на нужный срок, дубль и возврат. Только затем отдельно согласовать публичный запуск.

Будущий production webhook: **https://mysterion-international.com/api/getplatinum/webhook**. URL передаётся сервером в notificationUrl при создании каждой сделки. Пока код не опубликован, считать этот endpoint действующим нельзя. Возвраты через API эта реализация не создаёт: обрабатывает подтверждённые уведомления GetPlatinum; инициирование возврата — в кабинете провайдера.

## Подготовка Production — 21 ноября 2026

GETPLATINUM_API_KEY отсутствует в Production. В Cloudflare: Workers & Pages → mysterion-international → Settings → Variables and Secrets → Production → Add → Secret → имя GETPLATINUM_API_KEY → вставить организационный API-ключ кабинета kepvalera.getplatinum.ru → Save. Значение не отправлять в переписке. После добавления требуется новый deployment, затем владелец выполняет «Проверить GetPlatinum» в админке.

Несекретные переменные: GETPLATINUM_API_ORIGIN=https://kepvalera.getplatinum.ru и GETPLATINUM_LIVE_ENABLED=false. Webhook: https://mysterion-international.com/api/getplatinum/webhook. Терминал 156040 — справочный номер, не выдуманный параметр API. НДС нужно выбрать из allowedVats, возвращённых проверкой организации.

До отдельного разрешения не менять активного провайдера Tribute, gp_enabled=0, режим services и purchases_paused=1. Даже после установки ключа эти ограничения запрещают создание реальных оплат. Контрольная покупка требует отдельного согласования серверного флага, провайдера, НДС и существующих ограничений продаж. На временной странице пока остаётся информационная карточка действующей записи с отключённой оплатой: она не является подкастом «Как слово влияет на твою жизнь». Подтверждённого отдельного подкаста нет в каталоге; платная карточка подкаста 2500 RUB / 60 дней не публикуется. Для запуска такого товара нужны настоящий материал и его проверенная карточка, затем отдельная проверка сценария временной страницы; текущий checkout сохраняет запрет покупок режима services.

Актуальная официальная схема сверена: изменения относительно сохранённой версии относятся к подпискам (accessExpiresAt), не к используемым одноразовым платежам и webhook. Рекуррентные платежи не реализуются и не включаются.
