# Единый вход и RU/EN — 9 ноября 2026

## Что изменено

На всех существующих страницах и в защищённых серверных шаблонах используется одинаковая шапка: «Войти», после подтверждения сервером — «Личный кабинет», выход и ссылка «Панель управления» только для активного `admin` из D1. Редактор не получает эту ссылку; серверные разрешения существующей роли editor сохранены.

Для новой платформы (`VIEWER_PLATFORM_ENABLED=true`) административные роли дополнительно проверяются по `platform_staff` и `sub` проверенного Access JWT. Строка `users` и email/password-аккаунт `viewer_accounts` автоматически не переносятся и не повышаются; назначение owner требует явной привязки существующего Access subject.

`GET /api/media/session` возвращает только состояние собственной сессии, роль, доступность управления и время истечения. JWT, cookies, email и идентификатор пользователя в ответ не включаются. Ответ не кэшируется. На публичных страницах отсутствие сессии допустимо.

Подпись RS256, issuer, AUD, срок токена и роли проверяются на сервере. Административные операции принимают только административный AUD. Кабинет поддерживает общую Access Application или существующий отдельный Viewer AUD. Получение сессии не выдаёт права просмотра: покупки, ручные доступы, отзыв и сроки проверяются отдельно. `MEDIA_PAID_ENABLED` не изменён.

Кабинет различает приобретённые и предоставленные материалы, показывает срок доступа. При истечении сессии приватные элементы скрываются, просмотр прекращается, форма предлагает войти снова; выбранный для загрузки файл не сбрасывается. Выход использует штатный `/cdn-cgi/access/logout`.

Пользовательский интерфейс, формы, уведомления и переключатели содержат только RU/EN. Сохранённый выбор DE нормализуется в RU. Старые DE-значения в D1 сохраняются при редактировании существующих видео и коллекций, но API интерфейса их не показывает. Миграций и изменений удалённой D1 не выполнялось.

Основные файлы: `account.js`, `account.css`, общие HTML-шапки, `script.js`, UI-словари и страницы медиатеки, `media-worker/src/{auth,worker,members,page-guard,page-templates,site-header}.mjs`. Сборка `homepage.min.css/js` обновлена через `tools/build-homepage.mjs`; исходные фотографии и атмосферные анимации сохранены.

## Что вручную настроить в Cloudflare

1. Zero Trust → Access → Applications. Рекомендуется одна Self-hosted Application с общим AUD на текущем точном hostname `mysterion-international.pages.dev`, покрывающая:
   - `/media-login`, `/media-login.html`, `/media-login/*`;
   - `/admin-media`, `/admin-media.html`, `/admin-media/*`;
   - `/api/media/view/*` и `/api/media/admin/*`;
   - `/api/platform/admin/*` для новой административной панели.
2. Разрешите утверждённые группы администраторов и зрителей через выбранный IdP/OTP. Не используйте Bypass/Everyone. Даже прошедший Access зритель не получает административные права без соответствующей активной роли D1.
3. Pages → Settings → Variables and Secrets: `MEDIA_ACCESS_AUD` — AUD общей Application; `MEDIA_VIEWER_ACCESS_AUD` — тот же AUD либо отсутствует (используется административный AUD). `MEDIA_ACCESS_ISSUER` — существующий адрес команды Access. Существующая отдельная Viewer Application тоже поддерживается, но её AUD не даёт доступа к административным API.
4. Проверьте Cookie Path Attribute: cookie должна отправляться как на защищённый HTML, так и на API и `/api/media/session` (общий путь `/`). После изменения приложения выйдите и войдите заново, чтобы удалить старые cookies с конфликтующими путями.
5. Публичные страницы, публичный `/api/platform/catalog` и `/api/media/session` оставьте вне обязательного входа Access. Session endpoint сам проверяет переданный токен; административные API остаются защищёнными Access и серверной проверкой JWT, AUD и активной роли.
6. Оставьте `MEDIA_PUBLIC_ORIGIN` равным текущему pages.dev origin, D1 binding без изменений и `MEDIA_PAID_ENABLED=false`. Не переносите production-секреты в preview. Исключите приватные страницы и `/api/media/*` из пользовательских Cache Rules; ответы уже имеют `no-store`.
7. После сохранения переменных выполните новый deployment Pages. Проверьте в настоящем браузере администратора и отдельного обычного зрителя: вход, кабинет, выход, повторный вход, истечение сессии. Viewer должен получать отказ на административный API; анонимный посетитель должен свободно читать публичный сайт. Не присылайте JWT/cookies в чат.

Read-only проверка production 10 ноября 2026 года: `/admin-media.html` без сессии Access возвращает 302 на вход, но `/api/platform/admin/me` пока возвращает 200 HTML без Access challenge. Это ещё не опубликованный API маршрута, а ответ текущего сайта; до публикации добавьте `/api/platform/admin/*` в приложение Access и убедитесь без сессии, что запрос получает Access redirect. Метаданные защищённого ресурса подтверждают только HTML-путь, не API.

Access не создаёт автоматически пользователя D1 и права на видео. Для неизвестной подтверждённой личности кабинет показывает ожидание доступа; используйте существующее управление пользователями и ручными доступами. Фиктивных покупок создавать не нужно.

- 58 браузерных проверок медиатеки/загрузки и 20 проверок кабинета/управления доступами прошли; сценарии загрузки используют имитацию Bunny, а не реальные платные ресурсы.

- Скриншоты: `output/site-account-check/account-390.png` и `account-1440.png`. Это локальные тестовые данные, они не опубликованы как материалы служения.

Локальный тест выхода удаляет тестовую cookie; он не доказывает отзыв сессии на Cloudflare. Отдельная production-настройка Access выполняется владельцем, не этим commit.
