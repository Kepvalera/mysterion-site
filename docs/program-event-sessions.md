# Несколько Zoom-сессий в семинаре

Подготовлено локально на базе релиза `986d7afb32345a6ace53b57f309195a2261c6703`.
Публикация и применение миграции Production требуют отдельного подтверждения владельца.

## Работа владельца

«Курсы и уроки → Настройки онлайн-семинара → Сессии семинара».
Сначала сохраните общие настройки и общую Zoom-комнату. При первом добавлении
новой сессии существующая встреча сохраняется как «Сессия 1» в той же транзакции.
Дальше редактируйте её название и расписание в списке сессий.

Для каждой встречи доступны RU/EN, номер/порядок, дата и часовой пояс IANA,
продолжительность, спикер, время открытия Zoom, состояние и выбор комнаты.
«Общая комната» использует секрет из общих настроек семинара; «Отдельная» — свой.
Пустые секретные поля сохраняют прежние значения и никогда не заполняются сервером.
Изменение номера меняет порядок списка без изменения даты встречи.

Один семинар сохраняет одну регистрацию, один резерв места и один заказ.
Регистрация закрывается к началу первой неотменённой встречи, как у одиночного
семинара. Неопределённые и неуспешные платежи по-прежнему удерживают резерв места.
Добавление встречи само по себе не создаёт заказ и не списывает деньги.

При переносе последней встречи продлевается только право участия в этом семинаре.
Цена, платежи, снимки условий заказа и даты в истории платежей не переписываются.
Сокращение расписания автоматически не укорачивает выданные права. Явно укороченные
индивидуальные права не расширяются. Отозванные, заблокированные и оплаченные права
с подтверждённым возвратом не восстанавливаются. Независимые ручные права сохраняются.

В кабинете показаны ближайшая встреча и полное расписание. Расписание обновляется
при возврате на вкладку, локальном уведомлении админки и каждые 15 секунд в видимой
вкладке. Вход проверяется сервером заново, поэтому устаревший экран не разрешает Zoom.
Доступ к записям Bunny остаётся отдельным.

## API и безопасность

- Владелец: `GET/POST /api/platform/admin/events/:courseId/sessions`.
- Владелец: `PUT/DELETE /api/platform/admin/events/:courseId/sessions/:sessionId`.
- Участник: `POST /api/platform/events/:courseId/sessions/:sessionId/zoom`.
- Старый endpoint Zoom работает только для одиночных семинаров без строк сессий.
- Публичное расписание содержит только разрешённые метаданные, без ссылок и паролей.
- Секреты возвращаются только после проверки сессии пользователя, права участия,
  административных ограничений, принадлежности встречи, состояния и времени входа.
- CSRF, роли, подписи платежей и идемпотентность оплаты используют существующие механизмы.
- Изменения расписания используют revision семинара и встречи, атомарную транзакцию
  и журнал без Zoom-секретов. Параллельное изменение отклоняется, а не перезаписывается.
- Если есть любая регистрация, заказ, история прав или ограничений, DELETE отменяет
  встречу с сохранением истории. Физически удалить можно только будущую неиспользованную
  встречу пустого семинара; проверка повторяется внутри транзакции.
- Последняя сессия не удаляется: её можно отменить, чтобы не включился старый fallback.
- Окончательное удаление пустой архивной программы очищает только её конфигурацию;
  прежние запреты при наличии участников, финансов, прав и материалов сохранены.

Обычную Zoom-ссылку участник может переслать. Используйте пароль и Waiting Room;
индивидуальные Zoom-регистрации и интеграция с Zoom API не добавлялись.

## Миграция 0025_program_event_sessions.sql

Добавляет `program_event_sessions`, отдельную таблицу секретов
`program_event_session_secrets`, журнал расписания `program_event_session_history`
и индексы. Триггер нормализует конец нового оплаченного права при гонке webhook
с изменением расписания. Существующие строки таблиц не переписываются; массовой
конвертации одиночных семинаров нет. Триггеры возвратов и резервирования мест сохранены.

Репетиция backup → восстановление → миграция выполнена только на локальных данных:
проверены хеши всех 58 прежних таблиц, integrity_check и foreign_key_check.
Это не заменяет свежую резервную копию Production перед публикацией.

## Публикация и откат после отдельного разрешения

1. Проверить актуальный main и применимость подготовленного патча; повторить тесты при конфликтах.
2. Создать свежий полный экспорт Production D1 в закрытом каталоге, проверить SHA-256,
   доступ к файлу и восстановление в изолированную базу. Экспорт содержит секреты:
   не прикладывать его к GitHub, отчёту или публичному Preview.
3. На восстановленной копии применить 0025 и сравнить прежние строки/схему/внешние ключи.
4. Применить 0025 к Production, затем опубликовать сервер и интерфейс единым релизом
   через существующий процесс GitHub → Pages. Не менять провайдеров, продажи и режим сайта.
5. Проверить одиночный семинар, публичное расписание без секретов, кабинет и отказ
   неавторизованному запросу Zoom. Не создавать реальные платежи или тестовые права в Production.

До создания первых сессий можно вернуть предыдущий код, оставив добавочные пустые
таблицы и триггер (он не действует без сессий). После использования нескольких
встреч возврат старого кода небезопасен: он не понимает общее расписание. Предпочтителен
исправляющий релиз с сохранением схемы/истории. Не восстанавливать старую резервную
копию поверх работающей D1: это удалит более поздние покупки. Аварийное восстановление
допустимо только после отдельного согласования и переноса всех последующих данных.
