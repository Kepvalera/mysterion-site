# Регистрация и вход: задача №2

Подготовлено локально после публикации ручных продаж (15628fc).
Эти изменения пока не публиковались. Production D1, пользователи, пароли,
платежи и разрешения не изменялись; миграции не требуются.

## Интерфейс

- В существующих полях входа, регистрации и установки нового пароля добавлены
  кнопки глаза, включая повторный ввод. По умолчанию `type=password`.
  Повторное нажатие скрывает пароль. Кнопки имеют `type=button`, названия RU/EN,
  `aria-controls`, `aria-pressed`, видимый фокус и область нажатия 44×44 px.
- При смене формы, отправке, уходе со страницы и скрытии вкладки пароль снова
  скрывается. Значения не копируются и не сохраняются. Существующая очистка
  полей после запроса сохранена.
- После регистрации появляется отдельный блок «Подтвердите адрес электронной
  почты»: введённый email, инструкция открыть письмо и ссылку, напоминание о
  папке «Спам», кнопка «Отправить письмо повторно». Пароль повторно не нужен.
- Используется существующий `/api/viewer/resend-verification`, с прежними
  ограничениями частоты. Нет автоматических повторных POST или отправки писем
  при простом открытии страницы.
- Ошибка отправки отличается от инструкции о подтверждении. Повторная отправка
  восстанавливает процесс после сбоя, не меняя пароль ожидающего аккаунта.
- Ссылки подтверждения/сброса корректно открывают форму также из того же окна,
  где до этого было показано уведомление о регистрации.

## Достоверность уведомления

Раньше `sendToken` запускал отправку через `waitUntil`, проглатывал ошибку и
возвращал `202` до результата почтового сервиса. Теперь ответ для допустимой
отправки ждёт принятия запроса провайдером; отказ возвращает безопасный
`503 email_delivery_unavailable`. Ответ провайдера, email, токен и пароль в
журнал не выводятся. Принятие провайдером не гарантирует доставку во «Входящие».

Успешный API-ответ по-прежнему одинаков для новой регистрации, уже занятого
адреса и адреса, для которого повторная отправка неприменима. Поэтому нельзя
безусловно писать «Мы отправили письмо» по любому `202`: например, для уже
подтверждённого адреса письмо не отправляется. Публичный флаг существования
аккаунта или факта отправки для конкретного адреса не добавлен.

Текст после регистрации уточняет: «Если это ваша первая регистрация на этот
адрес, мы отправили письмо…». Для повторной отправки: «Если этот адрес
зарегистрирован и ещё не подтверждён, мы отправили письмо…». Далее показаны
запрошенные инструкции и адрес, введённый самим посетителем. При реальной
ошибке провайдера показывается «Не удалось отправить письмо».

Хэширование, сессии, проверки входа, подтверждение и одноразовое использование
токенов, сброс пароля и разграничение доступа не переписывались.

## Проверки

Изолированные аккаунты SQLite и локальный почтовый stub; реальных писем нет:

```text
node --import ./tools/register-viewer-wasm.mjs tools/test-auth-forms-browser.mjs
node --import ./tools/register-viewer-wasm.mjs tools/test-auth-mail-delivery.mjs
node tools/test-viewer-client.mjs
node --import ./tools/register-viewer-wasm.mjs tools/test-viewer-auth.mjs
```

Браузер использует настоящие HTML/CSS/JS и обработчик авторизации. Проверяются
RU/EN, ширины 320/390/768/1440, глаза обоих полей, регистрация, повторная
отправка, ссылка подтверждения, вход, изменение через профиль, восстановление,
установка нового пароля, ошибка отправки и восстановление после ошибки.
Отдельный тест доказывает, что HTTP-ответ ждёт провайдера и отказ не становится
успехом. Скриншоты и результаты: `output/auth-forms/`.
