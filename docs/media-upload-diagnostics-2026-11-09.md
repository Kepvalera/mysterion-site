# Диагностика остановки загрузки — 9 ноября 2026

**Уточнение после нового production-ответа:** подтверждена несовместимость `redirect: 'error'` с Cloudflare runtime. См. [воспроизведение в workerd и исправление](media-bunny-runtime-fix-2026-11-09.md). Разделы ниже описывают предыдущий этап диагностики.

## Что установлено

В production пользователь получил `503 {"error":"service_unavailable"}` на запросе upload; session и videos отвечают 200. В исходном `media-worker/src/worker.mjs` этот JSON формировался в общем `catch` только для исключения, которое не является `HttpError`. Поэтому этот ответ не доказывает неправильный ключ Bunny, отсутствие авторизации или конкретную ошибку D1.

Реальный маршрут: `POST /api/media/admin/videos/<id>/bunny/upload`. `functions/api/[[path]].js` импортирует `handle` непосредственно из `media-worker/src/worker.mjs` и передаёт ему Pages `env`. Название каталога media-worker не означает отдельный развёрнутый Worker; service binding к другому Worker здесь нет. Production-переменные должны находиться в этом проекте Pages.

Порядок выполнения: проверка конфигурации и origin → Access JWT и активная роль admin → блокировка bunny_leases → чтение черновика → серверный POST создания видео в Bunny → запись Video ID и audit_log в D1 → краткоживущая подпись TUS → снятие блокировки. Браузер начинает cross-origin TUS только после успешного ответа upload. CORS TUS не объясняет серверный 503 на этом предшествующем запросе.

Read-only Cloudflare-проверка подтвердила для Production: Library ID 803179, BUNNY_ENABLED и BUNNY_SECURITY_CONFIRMED равны true, CDN hostname подходит формату кода, три Bunny-ключа присутствуют как secret_text, binding MEDIA_DB присутствует, MEDIA_PAID_ENABLED=false. Привязанная D1 содержит ожидаемые videos, bunny_leases, audit_log и Bunny-колонки; внешний ключ блокировки указывает на videos. На момент проверки активных блокировок не было. Значения ключей не выводились. Наличие секрета не подтверждает его действительность в Bunny.

## Безопасные исправления

- Клиент показывает этап, понятное объяснение, разрешённый код ошибки, HTTP-статус, статус Bunny и Request ID. Неизвестные тексты и HTML от upstream не выводятся. FileList и форма сохраняются для повторной попытки.
- Сервер различает отказ API-ключа Bunny (401), запрет (403), отсутствие библиотеки/видео (404), rate limit (429), сбой провайдера, timeout, сеть и некорректный JSON. Тело ответа Bunny не раскрывается.
- Для внутренних исключений D1 загрузка получает отдельные этапы: bunny_store_lease_acquire, bunny_store_read, bunny_store_bind, bunny_store_lease_release. Отдельно обозначаются bunny_create и bunny_sign_upload. Классификация схемы/ограничений/параметров не раскрывает SQL или значения данных.
- Подтверждённый дефект обработки исключений: ошибка снятия блокировки в finally могла заменить исходную ошибку операции. Теперь сохраняется первичная ошибка; если сама операция успешна, сбой снятия блокировки сообщается отдельно. Ограниченный срок блокировки сохранён.
- Logs содержат только фиксированные event/phase/code, случайный Request ID, числовые статусы и разрешённое имя класса исключения. Нет JWT, cookies, email, API-ключей, подписей загрузки, исходных текстов исключений или тел провайдера.

Ни JWT/AUD/роли/origin, ни проверки источника TUS не ослаблены. Платный доступ не включён. Существующие видео и удалённая база не изменены; миграции не выполнялись.

## Проверки

- 230 серверных тестов на SQLite в памяти и имитации Bunny: авторизация, исходящие подписи, все новые upstream-ошибки, D1-ошибки, сохранение первичной ошибки при сбое cleanup, отсутствие секретов в диагностике.
- 64 браузерные проверки Chrome: RU/EN, 375/390/430/1440 px, прогресс, публикация, ошибка разрешения Bunny 401, неверная обложка до TUS, HTML вместо JSON, повторная попытка без второго черновика и без потери файла, платный блок и защита HTML.
- 5 отдельных TUS-сценариев: chunks, пауза/возобновление, обновление разрешения и запрет стороннего Location.
- Pages Functions собираются. Шаблонный поиск секретов не обнаружил находок.

Это локальные тесты с имитацией Bunny. Реальное создание/загрузка видео не выполнялись, чтобы не менять библиотеку и базу владельца. Исправление исходного production-сбоя пока не подтверждено: исторического исключения нет в предоставленном ответе. Новый код делает следующую попытку диагностируемой.

## Следующий шаг владельца

1. После успешного deployment обновить админ-панель с перезагрузкой ресурсов.
2. Открыть Cloudflare → Workers & Pages → mysterion-international → Production deployment → Functions/Real-time logs (название пункта зависит от интерфейса аккаунта).
3. Открыть существующий черновик и повторить действие один раз. При сетевом тайм-ауте сначала проверить статус, чтобы не повторять неизвестно завершившийся запрос вслепую.
4. Если снова ошибка, передать только JSON-поля `error`, `phase`, `requestId`, `upstreamStatus` и HTTP-статус либо соответствующую запись `mysterion_media_operation_failed`. Не передавать HAR, Request Headers, JWT, cookies, ключи и signed URL.
5. Если `bunny_auth_failed` / Bunny HTTP 401: вручную сверить Library API Key библиотеки 803179 с Secret BUNNY_API_KEY в Pages → Settings → Variables and Secrets → Production, затем выполнить новый deployment. Не использовать общий ключ аккаунта или embed-token key вместо Library API Key. Менять ключ по одному предположению сейчас не требуется.
6. Если код D1: не выполнять миграции автоматически. По phase и Request ID сначала определить, какой запрос не прошёл. Проверенная текущая схема не требует миграции по результатам этого аудита.

Официальная схема API: [Stream API и AccessKey](https://github.com/BunnyWay/documentation/blob/main/api-reference/stream/index.mdx). Серверный POST создания и браузерный TUS — разные этапы, Library API Key остаётся только на сервере.
