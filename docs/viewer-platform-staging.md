## Публикация только тестового проекта

Код платформы уже присутствовал в удалённой ветке как `d2725f2`.
Этот документ фиксирует проверку инфраструктуры. Префикс `[CF-Pages-Skip]`
предотвращает автоматические Pages-сборки для этого коммита, включая возможные
preview другого проекта. Затем применяется только явная команда Wrangler для
`mysterion-viewer-staging`, `--branch viewer-auth`, с allowlist-пакетом из
`tools/package-viewer-staging.mjs` и реальным commit hash.

Временный конфиг развёртывания создаётся из штатного `pages download config`
и не помещается в Git. Меняются только два несекретных флага тестового проекта:
`VIEWER_PLATFORM_ENABLED=true`, `MEDIA_ENABLED=true`. Существующие plaintext
настройки сохраняются, секреты не читаются вручную и не изменяются.
`MEDIA_PAID_ENABLED=false`, `BUNNY_ENABLED=false`. Никакой файл, backup или конфиг
из приватной папки не входит в публичный пакет.

Документация Cloudflare:
[пропуск Git-сборки](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/),
[конфигурация Pages через Wrangler](https://developers.cloudflare.com/pages/functions/wrangler-configuration/).

## Проверки и оставшиеся границы

Локально повторно прошли 79 проверок API платформы, 86 проверок миграций,
87 проверок viewer-auth, 32 проверки rate limiting, 20 проверок изоляции
кабинета, 5 сценариев TUS и сборка Pages Functions с двумя WASM-модулями.
Секреты паттерн-проверкой не обнаружены. Локальная D1/workerd поддерживает
новую схему, регистрацию, верификацию, вход и изменение профиля.

Staging-проверки без авторизации должны подтверждать публичный каталог и
невозможность изменять профиль, покупки, участников, права или публикации.
Нельзя выдавать конфигурационную блокировку админки за положительную проверку
её работы с настоящей ролью. Положительные административные сценарии пока
проверены локально; для staging требуется отдельное назначение владельца
после настройки/проверки административного Access issuer/AUD. Access в этой
работе не изменяется.

Настоящая авторизация существующего участника проверяется владельцем в своём
браузере: пароль, cookies и токены передавать не нужно. Работа реального
платного видеопотока, Bunny TUS и фактическая доставка писем не подтверждаются
локальными тестами. Платные сервисы и просмотр не включаются. Ограничение CPU
Argon2id на Free требует отдельного облачного измерения.

## Первичный владелец — только после отдельного подтверждения

1. Убедиться в точном проекте, UUID базы и свежей резервной копии.
2. Проверить административный Cloudflare Access JWT: подпись по JWKS,
   issuer, административный audience, срок и sub. Не брать sub из
   неподписанного payload или email. Не передавать JWT/cookies в чат.
3. Подтвердить у владельца именно проверенный sub и роль owner.
4. Подготовить точный SQL для просмотра, проверить пустоту `platform_staff`.
   Не создавать HTTP bootstrap endpoint, не выводить чувствительные данные.
5. Только после отдельного согласования выполнить один INSERT в эту staging
   D1 и проверить единственную активную owner-запись. production не затрагивать.

Шаблон, который не выполнялся и не содержит настоящего идентификатора:

```sql
INSERT INTO platform_staff(access_sub, role, active, created_at, updated_at)
SELECT '<VERIFIED_AND_SEPARATELY_APPROVED_ACCESS_SUB>',
       'owner', 1, unixepoch(), unixepoch()
WHERE NOT EXISTS (SELECT 1 FROM platform_staff);
```

После назначения отдельно проверить вход владельца, реальные права ролей,
ручное подтверждение тестовой заявки и отзыв/истечение прав. Не создавать
фиктивные оплаченные покупки или включать платный просмотр для этой проверки.
