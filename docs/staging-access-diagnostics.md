# Безопасная диагностика Access в staging

Включается только при одновременных условиях:

- `MEDIA_ACCESS_DIAGNOSTICS=true`;
- `MEDIA_PUBLIC_ORIGIN=https://mysterion-viewer-staging.pages.dev`.

Диагностическая строка содержит ровно четыре поля: `requestId`, `reason`,
`source` (`assertion` / `cookie`) и `audHasWhitespace` (boolean).
JWT, cookies, email, sub, пароли, значения переменных и тексты исключений
не записываются. Публичный ответ остаётся 401 `invalid_identity`, без причины.
Проверки подписи, issuer, AUD, срока и непустого sub обязательны как прежде.

Допустимые причины:

| reason | Значение / минимальная следующая проверка |
| --- | --- |
| token_format | Формат токена, алгоритм/заголовок, повреждённый JSON/base64 либо неоднозначная cookie. Источник указан отдельно. Не переключаться на cookie после отклонения явного assertion |
| issuer_mismatch | Сверить точный issuer с team domain; не принимать произвольный issuer |
| audience_mismatch | Сверить AUD именно staging-приложения, правильное окружение и наличие whitespace; не добавлять production AUD как обход |
| token_expired | Срок истёк или токен ещё не действителен (`iat`/`nbf` вне прежнего окна допуска); повторить вход и проверить время |
| subject_missing | Нет допустимого пользовательского sub; проверить, что используется пользовательский Access login, а не service token; проверку sub не убирать |
| jwks_fetch_failed | Сеть, timeout, HTTP или неверный JSON JWKS; не принимать токен при недоступных ключах |
| jwks_key_not_found | Нет ключа для kid; проверить ротацию и необходимость однократного безопасного обновления кэша |
| signature_invalid | Импорт ключа или проверка подписи не удались; подпись не отключать |

## Как получить причину

1. Cloudflare → Workers & Pages → **mysterion-viewer-staging** → открыть
   актуальное развёртывание → Functions / Logs → Real-time logs / Begin log stream.
   В разных версиях Dashboard раздел может называться Observability → Logs.
2. Запустить поток до повторного входа.
3. Открыть canonical `/admin-media.html`, пройти Access и повторить ошибку.
4. В DevTools → Network у окончательного ответа Pages Worker найти
   `X-Mysterion-Request-ID`. У `/api/platform/admin/me` ID также есть в JSON.
   У промежуточного Access-редиректа такого ID может не быть.
5. Найти console-строку с тем же `requestId` и прочитать `reason`.
   Если нужно сообщить результат, передавать только эти четыре поля.
   Не передавать полное tail-событие, HAR или Request Headers.

Диагностическая причина до криптографической проверки описывает место отказа,
а не подтверждённые сведения о пользователе. Выдавать owner можно только после
полной успешной проверки JWT и отдельного согласования.

После определения настоящей причины исправляется только соответствующая ветвь,
затем диагностику можно отключить staging-флагом и повторным staging deployment.
Положительный локальный тест не доказывает, что настоящий JWT пользователя
прошёл проверку в опубликованной Functions.
