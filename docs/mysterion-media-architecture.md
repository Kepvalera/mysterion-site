# MYSTERION MEDIA — этап 1

## Что реализовано

`media.html` — отдельный каталог с поиском, категорией, годом, типом доступа, постраничной загрузкой и диалогом проигрывателя. Контент приходит из API, а не из массива в HTML. RU/EN/DE, мобильное меню, управление клавиатурой. До подключения API отображается честное состояние подготовки. Старые страницы не заменяются.

`admin-media.html` — оболочка управления: список, создание, редактирование переводов, публикация бесплатных записей, загрузка обложки и удаление. Элементы управления появляются только после успешной серверной проверки. Скрытие интерфейса не является защитой: каждый административный запрос независимо проверяется сервером.

`functions/api/[[path]].js` подключает общий Workers-модуль. `_routes.json` отправляет в Functions только `/api/media`; остальные страницы остаются статическими. Сборка `homepage.min.css/js` не изменяется: новые стили и скрипты загружаются только на новых страницах. Главная получила ссылку на реальный каталог.

API закрыт по умолчанию: без `MEDIA_ENABLED=true`, привязок и параметров Access возвращает 503. Проверяется подпись RS256 токена Access по доверенному JWKS, issuer, audience, срок и роль пользователя в D1. Заголовок с email сам по себе ничего не разрешает. Начальные администраторы не создаются автоматически.

Записи редактируются с optimistic locking (`revision`), операции и аудит выполняются одним D1 batch. Удаление логическое, покупки и аудит сохраняются. Публичные запросы не выдают черновики, будущие публикации, удалённые записи, ключи R2 или идентификаторы исходного видео. Endpoint воспроизведения выдаёт источник только для опубликованного бесплатного материала. Обложки проверяются по сигнатуре; SVG запрещён; лимит 2 МБ. Все записи проходят ограничение тела, проверку Origin, подготовленные SQL-запросы и валидацию.

## Что намеренно не включено

**Платные публикации и воспроизведение заблокированы в серверном коде**, включая случайно импортированную опубликованную платную строку. Нет checkout, приёма платежей, ручного подтверждения оплаты, пользовательского кабинета или выдачи прав из браузера. Платные метаданные доступны администратору только как черновики. YouTube допускается только для бесплатного видео: доступ «по ссылке» не защищает платное содержимое.

Таблицы `users`, `purchases`, `entitlements` задают модель следующего этапа. Роли: admin — публикация, обложки, удаление; editor — создание/редактирование черновиков; viewer — будущий зритель. Для платного просмотра потребуется отдельная серверная реализация: проверенный пользователь, действующая неревокированная выдача, неистёкший срок, оплаченная и невозвращённая покупка, проверка принадлежности материала и повторная проверка каждого запроса к видео. Эта модель пока **не является работающей системой покупок**.

Следующий этап требует подписанных webhook, идемпотентности события провайдера, сопоставления суммы/валюты/материала, атомарного создания покупки и права, обработки возврата/отзыва, защиты от повторного использования и тестов Range-запросов. До этого ограничения платного воспроизведения снимать нельзя.

R2 позволяет хранить закрытые MP4/WebM и отдавать их через Worker с Range. Это не адаптивный видеохостинг и не DRM. Для больших объёмов и адаптивного качества следует отдельно согласовать Cloudflare Stream и его стоимость. На этом этапе никакие платные ресурсы не создаются.

## Настройка Cloudflare — требуется оператор

1. Подтвердить отдельное staging-окружение Pages, новый D1 и **private** R2. Не включать публичный `r2.dev` или публичный домен бакета. Ничего из этого текущая задача автоматически не создаёт.
2. После отдельного согласования применить `media-worker/migrations/0001_media.sql` сначала в staging. Продакшен-миграции не выполнялись.
3. В Pages привязать D1 как `MEDIA_DB`, R2 как `MEDIA_BUCKET`. Параметры: `MEDIA_ACCESS_ISSUER=https://<team>.cloudflareaccess.com`, `MEDIA_ACCESS_AUD=<application audience>`, `MEDIA_PUBLIC_ORIGIN=https://<точный домен без слеша>`. Начать с `MEDIA_ENABLED=false`.
4. Создать Cloudflare Access application для `/admin-media*` и `/api/media/admin/*` на том же домене с одним audience, ограниченным allow-list и MFA. Защитить также preview-домены или оставить их выключенными. Проверить Access cookie, Origin и прямые API-запросы.
5. Получить `sub` подтверждённой личности Access и отдельно одобрить создание начальной строки `users` с ролью admin. Не выдавать роль по произвольному email из запроса. Секреты/пароли в Git не нужны: привязки Cloudflare дают доступ к ресурсам без S3-ключей.
6. Загрузить только реальные подтверждённые видео в закрытый R2 (`videos/...mp4` либо `.webm`) или использовать подтверждённый YouTube ID. Сначала сохранить черновик и проверить три перевода и обложку. Загрузка больших видео через браузер в этот этап не включена: форма принимает существующий приватный ключ объекта, а обложки загружаются через API.
7. Проверить резервное копирование, лимиты запросов/WAF для административного API, размеры хранилища, аудит и отдельный staging. Включить `MEDIA_ENABLED=true` только после интеграционных тестов реального Access/D1/R2. В случае ошибки вернуть false.

Для настройки нужны доступ оператора к Pages/Access, имя команды и audience Access, точный домен, идентификатор отдельно согласованного D1, имя закрытого R2, подтверждённый Access sub первого администратора. Не присылать пароли или секретные токены в исходники.

## Ограничения и эксплуатация

Административный список ограничен последними 200 записями; для большого каталога понадобится серверная пагинация управления. Старые обложки сохраняются как недоступные orphan-объекты: отдельная безопасная очистка после периода хранения ещё не реализована. Обложка доступна публично только через проверку опубликованной записи. Публикация YouTube не подтверждает существование/права видео автоматически — администратор обязан проверить материал. Политики Access/MFA, реальная доставка R2 и ограничения аккаунта требуют проверки в staging.

## Проверка

`tools/test-media.mjs`: 37 успешных проверок; временная SQLite в памяти, реальные RSA-подписи, проверка неверных identity/ролей/Origin, валидации, optimistic locking, публикации и закрытого платного доступа. Никаких seed-материалов в продакшен. `tools/check-media-browser.mjs`: 27 проверок; Chrome, 375/390/430/1440 и RU/EN/DE, ошибки JS, переполнение, мобильное меню, закрытое состояние admin, безопасный вывод заголовка и удаление iframe после закрытия плеера на локальных ответах API. Ошибок JS и переполнения не обнаружено. В одном локальном прогоне DCL 35 мс / load 63 мс; это измерения на машине разработчика, не показатели мобильного интернета и не Core Web Vitals продакшена. Новые страницы не создают Canvas и постоянных requestAnimationFrame. Скриншоты в `output/media-check/`, не включаются в публикацию. Safari и реальный Cloudflare Access этими тестами не проверяются.
