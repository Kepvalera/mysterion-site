# Устойчивая загрузка Bunny Stream

## Исправленный путь

Админка определяет MysterionBunnyUpload один раз, в bunny-upload.js. Раньше подключённый позже bunny-upload-resume.js заменял класс и мог автоматически начинать новую TUS-сессию с нуля после 404 прямо во время PATCH. Совместимый URL файла сохранён, но он больше не переопределяет загрузчик.

- Основной фрагмент — 1 МиБ. После сбоя уменьшается до 512/256 КиБ. Файл передаётся Blob.slice, целиком в память не читается.
- Реальный XMLHttpRequest.timeout — 180 секунд. Отдельный контроль отсутствия отправки или ответа — 45 секунд. HEAD/POST ограничены 30 секундами.
- Процент означает подтверждённые Bunny байты. Отправленный браузером фрагмент и ожидание Upload-Offset показаны отдельно.
- Успешный PATCH требует 204 и точного ожидаемого Upload-Offset. Отсутствующий заголовок не превращается в 0. После потерянного ответа, 409, обрыва или тайм-аута сначала выполняется HEAD. Повторная отправка без известного offset запрещена.
- При отсутствии продвижения допускается не более пяти PATCH-попыток (первая + четыре повтора). Ошибка HEAD останавливает передачу, не создавая новую сессию.
- 404/410 не запускает автоматический сброс в ноль. Новая TUS-сессия возможна только после отдельного подтверждения пользователя и остаётся привязана к прежнему Bunny-видео. Автоматического создания второго видео нет. За один экземпляр загрузчика допускается не более одного такого перезапуска.
- Если сервер сообщает позицию меньше уже подтверждённой в этой вкладке, загрузка останавливается с ошибкой offset. После перезагрузки вкладки источником истины остаётся HEAD, а не прежний процент отправки.
- POST создания TUS-сессии не повторяется автоматически после потерянного ответа. Подписанные заголовки, URL сессии и API-ключи не входят в диагностику и не записываются в localStorage.

Для /admin-media существующий CSP разрешает connect-src https://video.bunnycdn.com. Сам бинарный PATCH идёт прямо в Bunny, не через Cloudflare Pages. Блокировку CORS, сети или VPN на конкретном компьютере нельзя исключить одним ответом POST 201: для неё нужны результаты реального PATCH и HEAD из браузера владельца.

## Проверки, которые уже выполнены

Изолированная имитация проверяет потерянный ответ после полной/частичной записи, отсутствующий заголовок, нулевой offset, 401/409, тайм-аут, неизвестный HEAD, остановку, обновление подписи, возобновление и файл 3,5 ГиБ с началом на 40%. Большой файл в этом тесте виртуальный — это не реальная отправка 3,5 ГиБ.

Реальный XMLHttpRequest передаёт 64 МиБ по HTTP на локальный cross-origin TUS-сервер с CORS preflight. Сервер обрывает ответ, сохраняет частичный фрагмент и оставляет один PATCH без ответа. Передача завершается после сверки offset и паузы, SHA-256 тела совпадает с исходным. Это проверка реальной передачи байтов, но не отправка в Bunny.

Браузерный тест формы подтверждает: «Загрузить файл в черновик» оставляет запись draft/free, не создаёт уроков, покупок и доступов. Повтор использует тот же Bunny ID и ту же TUS-сессию. Все объекты этого теста — локальные имитации.

## Реальная проверка — только владельцем после отдельного разрешения

Во время разработки реальные объекты Bunny не создавались и не удалялись. Текущая загрузка 3,5 ГБ и существующие видео не использовались. Реальный результат Bunny пока не подтверждён.

1. Войти владельцем в https://mysterion-international.com/admin-media и обновить страницу после публикации исправления.
2. Только после отдельного разрешения на создание тестового объекта открыть «Видеоматериалы → Добавить видео». Название — TEST Bunny Upload. Источник — Bunny Stream, доступ — бесплатный, стоимость 0, продажа выключена, статус draft. Не использовать раздел конференций/уроков и существующие видео.
3. Выбрать отдельный нечувствительный тестовый MP4. Не выбирать текущий файл 3,5 ГБ. Нажать «Загрузить файл в черновик», а не «Загрузить и опубликовать». Это действие создаёт один объект Bunny для нового черновика и начинает реальную передачу.
4. Проверить увеличение строки «Подтверждено Bunny». В Network у PATCH должен появляться 204, а Upload-Offset — увеличиваться на фактически принятые байты. Диагностика различает передачу и ожидание подтверждения.
5. Для проверки восстановления нажать «Приостановить», затем снова «Загрузить файл в черновик» в той же записи с тем же исходным файлом. Не добавлять новый материал. После перезагрузки заново выбрать тот же файл с тем же именем/размером/датой изменения: существующая серверная запись resume проверяется по fingerprint.
6. При 404/410 не подтверждать старт с нуля автоматически. Если сессия действительно удалена Bunny, восстановить её прежние байты нельзя; перезапуск в том же видео требует осознанного согласия.
7. После завершения передача должна иметь confirmed_bytes=file_bytes. Статус записи остаётся draft. Обработка кодеков Bunny — отдельный этап после передачи; её ожидание не означает зависший PATCH.
8. Нажать «Копировать диагностику загрузки» и передать только полученный JSON. Он содержит счётчики, offset, размеры, стадии и HTTP-статусы последних событий; URL, заголовков авторизации, ключей и имени файла в нём нет. Не передавать HAR, cookies или подписи.

Ничего не удалять автоматически после проверки. Публикация и удаление тестового объекта требуют отдельных действий владельца.

Источники: https://bunny.net/docs/stream/tus-resumable-uploads и https://tus.io/protocols/resumable-upload .
